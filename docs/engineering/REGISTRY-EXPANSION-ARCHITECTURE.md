# Registry Expansion Architecture — Modern IE on Forge 1.7.10

Date: 2026-09-11
Status: DESIGN GATE

## Problem
The recovered Forbidden baseline uses 1.7.10 metadata-packed block families.
That design is world-compatible and must remain frozen, but it cannot absorb the entire 1.21.1 surface.

Current confirmed occupancy:
- `metalMultiblock`: metas 0–14 are assigned; only meta 15 remains.
- `metalDevice2`: metas 0–12 are assigned.
- `metalDecoration2`: metas 0–3 are assigned.
- GUI IDs currently occupy 0–14.

The project MUST NOT remap an existing metadata value to a new semantic meaning.

## Decision
Legacy families remain immutable compatibility islands.
New 1.21.1 backports use new registry names and new block families when legacy capacity is insufficient.
A free metadata value may be used only when:
1. source/runtime search proves it was never assigned or reserved;
2. existing worlds show no historical use;
3. the assignment is documented in the feature gate;
4. the feature does not make future expansion harder than a new block family would.

## Proposed namespace policy
Keep mod id `ImmersiveEngineering` for continuity, but introduce explicit new registry names instead of overloading exhausted blocks.

Candidate families:
- `metalMultiblock2` — later formed multiblock states only;
- `metalDevice3` — later standalone metal devices;
- `metalDecoration3` — later decorative/engineering components;
- `woodenDevice2` — later wooden devices;
- dedicated blocks for high-complexity devices when metadata packing harms clarity or rendering.

Names are provisional until collision audits are complete.
No existing registry name is renamed or deleted.
## Multiblock rule
`metalMultiblock` meta 15 is NOT automatically consumed by the next feature.
Because only one legacy slot remains, it is treated as strategic reserve until a specific compatibility benefit justifies using it.

The default for Alloy Kiln, Mixer, Sawmill, Shelf, Chunk Loader and Radio Tower is a new formed-state registry family unless archaeology proves a stronger reason otherwise.

## GUI IDs
GUI IDs are integers and are not constrained to metadata width, but 0–14 are frozen.
New GUI IDs must be allocated monotonically from an audited registry table, never by ad-hoc literals in feature branches.

Proposed rule:
- legacy/frozen: 0–14;
- modern backport allocation begins at 32;
- 15–31 remain reserved for compatibility branches and already-planned legacy continuations.

This creates an intentional visual separation in audits and prevents accidental reuse.
## TileEntity IDs
Existing `registerTile()` derives IDs as `ImmersiveEngineering:<ClassNameWithoutTileEntity>`.
That historical convention remains valid for old classes.

New classes must receive a pre-registration collision audit against:
- every currently registered IE TileEntity ID;
- recovered production worlds/configs when available;
- aliases from prior community forks we intentionally support.

No new TileEntity may reuse an old string merely because its implementation was replaced.
If a modern feature supersedes a legacy concept, migration requires an explicit data contract rather than silent ID reuse.

## Item/block registry compatibility
World compatibility has priority over source aesthetic purity.
A modern feature does not need the same internal registry topology as NeoForge 1.21.1; it needs stable 1.7.10 identities and equivalent gameplay semantics.

New blocks should prefer dedicated registry names when they have complex TileEntities, renderers or future variants.
Metadata packing remains acceptable for simple homogeneous decoration families where all 16 states share lifecycle and renderer behavior.
## Audited capacity snapshot
Generated by `tools/audit_registry_surface.py`:
- `BlockMetalDevices`: 0–15 occupied, zero free;
- `BlockMetalDecoration`: 0–15 occupied, zero free;
- `BlockMetalMultiblocks`: 0–14 occupied, meta 15 free;
- `BlockMetalDevices2`: 0–12 occupied, metas 13–15 free;
- `BlockMetalDecoration2`: 0–3 occupied, metas 4–15 free;
- GUI IDs: 0–14 occupied, no duplicates;
- registered TileEntity IDs: 61, no duplicates.

Machine-bearing capacity must not be inferred solely from free metadata. A free state in an old family can still be rejected if its renderer, ItemBlock or TileEntity switch structure makes the addition fragile.

## Gate for every feature
Before registry code is accepted, regenerate `IE-1.7.10-REGISTRY-SURFACE.json` and prove:
- no duplicate metadata constants within each family;
- no duplicate GUI ID;
- no duplicate TileEntity ID;
- no removed legacy identity;
- old-world load/remap test remains pending until runtime evidence exists.

Status: **DESIGN PASS; runtime/world migration evidence remains mandatory per feature.**
